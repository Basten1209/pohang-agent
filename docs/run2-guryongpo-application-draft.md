## 페이지 1

## 1. 아이디어 발상 동기

포항에서 러닝 행사를 마친 외지 참가자가 구룡포·호미곶을 방문하려면 대회장 밖으로 추가 이동해야 한다. 정확한 이동시간은 행사 장소와 출발 시각에 따라 달라지지만, 완주 직후의 참가자가 피로도·귀가 마감·교통·관광지 운영시간을 따로 확인해 일정을 다시 짜기는 어렵다. 이 제안은 관광정보 부족보다 **완주 후 남은 시간과 몸 상태를 반영한 이동 결정의 부재**를 해결하려 한다.

핵심 사용자는 **타지역에서 10km 대회에 참가하고 자가용으로 당일 귀가하는 러너**다. 사용자가 “17시 전에 포항을 떠나야 하고 많이 걷고 싶지 않아요”라고 입력하면, RUN2구룡포는 귀가 시각과 보행 선호를 구조화해 확인받는다. 완주 뒤에는 실제 기록과 고정형 증상 확인 결과를 더해 `지금 이동 / 짧게 방문 / 관광 취소 / 의료지원 우선` 중 하나를 제안한다.

## 2. 서비스 내용 및 주요 특징

### 이용 흐름

1. **대회 전:** 자연어 또는 입력 항목으로 종목·목표기록·귀가시각·이동수단을 받는다. LLM이 자연어에서 일정 제약을 추출하고, 사용자가 확인하면 목표 페이스와 완주 후 예비 일정을 저장한다.
2. **완주 직후:** 실제 기록과 `양호 / 많이 지침 / 통증 / 어지럼·메스꺼움`을 입력받는다. 서버는 E-UM 교통·대기, TourAPI 관광정보, Kakao Mobility 차량 ETA를 다시 조회한다.
3. **완주 후·관광 중:** 결정 규칙이 위험 증상과 시간 예산을 먼저 계산한다. LLM은 이 결정을 바꾸지 않고, 허용된 장소 안에서 일정과 이유를 설명한다. 교통이나 운영정보가 달라지면 같은 규칙으로 일정을 줄이거나 취소한다.

### 판단 방식

```text
여유시간 = 귀가마감 - 현재시각 - (회복 + 왕복이동 + 체류 + 여유)
```

- 위험 증상이 있으면 시간 계산을 중단하고 현장 의료지원을 안내한다.
- 여유시간이 부족하면 장소와 체류시간을 줄이고, 최소 코스도 불가능하면 관광을 취소한다.
- **시연 예시(가정값):** 14시 완주, 17시 30분 귀가 출발이면 210분을 쓸 수 있다. 회복 30분·왕복 100분·관광 90분·여유 30분은 총 250분이므로 장기 코스를 제외한다. 관광을 45분으로 줄여 총 205분이 되면 복귀 마감과 함께 단축 코스를 제시한다.
- E-UM `INT_S07_005`의 `cntPerc`는 특정 도로의 ETA가 아니라 구룡포 전체 장비의 통합 혼잡 신호다. 프로토타입에서는 관리자 설정값에 따라 보수적인 교통 여유시간을 더하고, 실제 차량 ETA는 Kakao Mobility가 계산한다.
- E-UM `INT_S01_004`는 시연 대상 장비 `id`를 지정해 조회한다. `logDateTime`과 대기·기상 측정값을 관측 시각과 함께 표시하되 의료적 기준으로 해석하지 않는다.

기존 러닝 앱과 관광 앱 사이에서 사용자가 일정을 다시 만드는 대신, RUN2구룡포는 **대회 전에 저장한 하루 계획을 실제 완주 결과와 구룡포 데이터로 다시 계산**한다. 가족·크루·대중교통 일정은 동일한 시간 예산 모델을 확장한 후속 범위로 둔다.

## 페이지 2

## 3. 서비스 목표 및 구현 방법

### 본선 MVP

본선에서는 `자연어 일정 입력 → 레이스 계획 저장 → 완주 결과 입력 → E-UM 실제 호출 → 규칙 기반 결정 → LLM 설명과 관광 일정 → 조건 변화 재계산`을 하나의 PWA로 시연한다. 대표 데모는 10km 당일 귀가 사용자 한 명의 정상·시간 부족·위험 증상 시나리오다.

### 데이터와 결정의 연결

| 데이터 | MVP에서 하는 일 | 제출 전 확인 |
| --- | --- | --- |
| **E-UM 교통 `INT_S07_005`** | `GET /dpg/traffic/congestion`의 측정 일시 `hour`와 통합 혼잡률 `cntPerc`를 표시하고 교통 여유시간의 보조 신호로 사용 | 서비스 키 실제 응답 |
| **E-UM 대기 `INT_S01_004`** | `GET /dpg/atmosphere/device/realtime`을 지정 장비 `id`로 호출해 `logDateTime`, `pm10`, `pm25`, `temp`, `humi`, `winsp`, `windir`를 표시 | 장비 ID·서비스 키 실제 응답 |
| **TourAPI·Kakao Mobility** | `locationBasedList2` 등으로 후보를 찾고, `GET /v1/directions`로 자가용 왕복 ETA를 계산 | 구룡포 후보·경로 실제 응답 |

PWA 요청은 서버의 데이터 통합 계층으로 전달된다. 통합 계층은 좌표·시각·단위·갱신시각을 맞춘 뒤 결정 규칙에 넘긴다. LLM에는 확정된 결정, 허용 장소, 귀가 마감만 제공한다. API가 실패하면 최근 캐시와 검증된 정적 후보를 사용하고, 경로는 Google Maps URL로 열어 데이터 기준시각과 한계를 함께 표시한다.

### 3주 구현 범위

- **1주차:** 핵심 사용자 PWA, 레이스 계획·페이스 계산, E-UM 교통·대기 실호출
- **2주차:** 시간 예산·위험 증상 규칙, TourAPI·Kakao 현재 길찾기, LLM 구조화 출력
- **3주차:** 일정 재계산, 키 누락·401·timeout·stale·빈 결과 테스트, 3개 대표 시나리오 시연

대중교통 실시간 도착, Apple Watch, 공식 기록 자동 연동, 관광패스·할인·전용 셔틀은 MVP에서 제외한다.

## 4. 기대효과 및 활용방안

- 시연에서는 `관광계획 저장 → 완주 후 재계산 → 길찾기 실행` 전환을 측정해 추천이 실제 이동 시도로 이어지는지 확인한다.
- 실증 단계에서는 시간대별 이동 시도와 취소 이유를 익명 집계한다. 포항시와 행사 운영자는 이 자료를 다음 행사에서 관광 안내 시점과 추천 코스를 조정하는 근거로 활용할 수 있다.
- 지역 매출·숙박 증가를 MVP 성과로 단정하지 않는다. 초기 검증 범위는 구룡포 이동을 시작했는지까지다.

## 5. 기타 사항

- **안전:** 서비스는 의료 진단이나 안전을 보장하지 않는다. 통증·어지럼·메스꺼움 입력 시 관광 일정을 만들지 않고 현장 의료진 또는 119 안내를 우선한다.
- **개인정보:** 상세 위치와 자가 컨디션은 기능 수행 중에만 사용한다. 서버에는 결정 상태와 익명 전환 이벤트를 우선 저장하며 원본 위치 이력은 남기지 않는다.
- **완료 기준:** E-UM 2종의 HTTP 200·기대 필드, 키 누락·401·timeout·stale·빈 관광 결과·경로 실패, LLM 출력 스키마 오류를 확인한다. 웨어러블 없이 전체 흐름을 완료해야 한다.
