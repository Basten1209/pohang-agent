## 1. 아이디어 발상 동기

경주는 보문관광단지 안에서 마라톤을 열어 달리는 경험과 관광을 같은 권역에 배치하고, 제주는 관광업체 참여를 대회 전에 조직해 스포츠 행사를 여행 경험으로 확장한다. 반면 포항은 러닝 행사와 구룡포·호미곶이라는 대표 관광자원을 모두 보유했지만, 대회 장소와 남부 관광권 사이의 추가 이동을 완주자가 직접 판단해야 한다. 완주 직후에는 피로, 귀가 시각, 교통, 날씨, 관광지 운영시간을 한꺼번에 확인하기 어려워 관광지 정보가 있어도 실제 이동으로 이어지기 어렵다.

**RUN2구룡포**는 관광지를 나열하는 앱이 아니라, 대회 전부터 러너의 목표 페이스와 하루 일정을 계획하고 완주 후 실제 기록·자가 컨디션·구룡포 데이터를 다시 계산해 “지금 무엇을 할 수 있는가”를 결정하는 AI Agent다. 핵심 질문은 다음과 같다.

> 지금 출발하면 내 상태와 귀가 일정에 맞춰 구룡포·호미곶을 방문할 수 있는가?

## 2. 서비스 내용 및 주요 특징

### 서비스 흐름

1. **대회 전:** 종목·목표기록·귀가시각·이동수단을 입력하면 목표 페이스, 체크포인트 통과시각, 기상 주의사항과 완주 후 예비 관광계획을 만든다.
2. **대회 중:** 웨어러블 없이도 확인 가능한 1km·체크포인트 단위 페이스 카드와 예상 완주시각을 제공한다.
3. **완주 직후:** 실제 기록과 `양호 / 많이 지침 / 통증 / 어지럼·메스꺼움`을 입력받고 교통·대기·날씨·관광정보를 새로 조회한다.
4. **완주 후:** `바로 이동(GO) / 회복 후 이동(DELAY) / 코스 축소(SHORTEN) / 실내 대안(INDOOR) / 관광 취소(CANCEL) / 의료 우선(MEDICAL_FIRST)` 중 하나를 결정하고, 이동·체류·복귀마감이 포함된 일정을 제시한다.
5. **관광 중:** 교통·환경·운영정보 변화 또는 사용자 요청에 따라 장소를 줄이거나 실내 일정으로 다시 구성한다.

### 타깃과 차별성

- **10km 당일 귀가형:** 기차·버스 마감에서 역산한 단축 코스로 귀가 불안을 낮춘다.
- **가족 동반 하프형:** 러너의 피로를 반영해 식사·휴식·실내 중심으로 가족 일정을 유지한다.
- **크루 1박형:** 구성원별 완주시간을 통합해 당일 구룡포와 다음 날 호미곶 일정을 연결한다.

기존 러닝 앱이 운동 종료에서 끝나고 관광 앱이 사용자의 운동 맥락을 모르는 것과 달리, RUN2구룡포는 **대회 전에 저장한 계획을 실제 완주 결과와 도시 데이터로 수정**한다. 확인되지 않은 관광패스·할인·전용 셔틀·공식 기록 연동은 사용하지 않으며, PWA로 구현해 별도 설치와 Apple Watch 없이 전체 흐름을 수행한다.

## 3. 서비스 목표 및 구현 방법

### 구현 목표

본선 MVP에서 `대회 계획 생성 → 페이스 카드 → 완주 후 Recovery Gate → E-UM 실제 호출 → 방문 상태 결정 → 관광 일정·길찾기 → 조건 변화 재계획`을 하나의 PWA로 시연한다. 단순 질의응답을 넘어 판단·추천·알림·시각화를 제공한다.

![PWA, Application API, AI Orchestration, 외부 데이터로 구분하고 안전 판단은 규칙, 설명은 LLM으로 분리한 시스템 아키텍처](assets/run2-guryongpo/application-system-architecture.png)

### Application System Architecture

- PWA는 `POST /api/race-plans`, `POST /api/post-race/decision`, `POST /api/itineraries/replan`을 호출한다.
- API Orchestration Layer가 E-UM·기상청·TourAPI·Kakao Mobility를 병렬 호출하고 Adapter가 좌표·시각·단위·신선도를 표준화한다.
- Rule Engine이 위험 증상과 `남은 시간 - (회복 + 이동 + 관광 + 복귀 + 여유)`를 계산해 상태 코드를 확정한다. 위험 증상 입력 시 관광을 생성하지 않고 현장 의료지원을 우선 안내한다.
- LLM은 확정된 상태를 변경하지 않고, 허용된 관광 후보 안에서 일정과 판단 근거를 자연어로 설명한다.
- API 오류·빈 응답에는 최근 캐시, 검증된 정적 관광 후보, Google Maps URL을 사용하고 갱신시각과 한계를 표시한다.

### 외부 API와 데이터

| 구분 | 실제 호출·활용 내용 |
| --- | --- |
| **E-UM 교통 `INT_S07_005`** | `GET /dpg/traffic/congestion`의 `hour`, `cntPerc`로 시간대별 혼잡 신호와 출발시각을 조정 |
| **E-UM 대기 `INT_S01_004`** | `GET /dpg/atmosphere/device/realtime`의 `logDateTime`, `pm10`, `pm25`, `temp`, `humi`, `winsp`, `windir`를 표시하고 실내·실외 일정 판단을 보조 |
| **기상청 단기예보** | `getVilageFcst`, `getUltraSrtFcst`, `getUltraSrtNcst`의 기온·강수·습도·풍속을 대회·관광 시간대에 적용 |
| **한국관광공사 TourAPI** | `locationBasedList2`, `detailCommon2`, `detailIntro2`, `detailImage2`, `searchFestival2`로 관광 후보·소개·운영정보·행사를 조회 |
| **Kakao Mobility** | `GET /v1/directions`, `GET /v1/future/directions`의 거리·예상 소요시간으로 자가용 이동·복귀 시간을 계산 |
| **버스** | 포항시 노선정보는 정적 안내로 사용하고, TAGO는 포항 도시코드·정류소 실응답 확인 후에만 실시간 도착 기능으로 제공 |

대회 코스·출발시각·급수 지점은 공식 운영자료를 관리자 데이터로 등록하고, 공식 기록 연동 전에는 사용자가 실제 기록을 입력한다. E-UM 키는 서버 환경변수에만 저장한다. E-UM 종합플랫폼의 행사 정보는 공개 API 계약 확인 전 실연동으로 주장하지 않고, 행사 검색은 TourAPI를 우선한다.

## 4. 기대효과 및 활용방안

- 완주자의 `대회 전 관광계획 저장 → 완주 후 재계산 → 길찾기 실행 → 구룡포 도착 확인` 퍼널을 측정해 단순 추천이 실제 이동으로 이어졌는지 검증한다.
- 주요 KPI는 관광 사전 저장률, 완주 후 재계산률, 길찾기 실행률, 동의 기반 도착 확인율, 평균 방문 장소 수·체류시간, 취소·축소·실내 전환율이다.
- 익명 집계로 행사별 구룡포 방문 수요, 이동 시간대, 자가용·대중교통 비율, 관광 포기 이유를 파악해 향후 교통·관광시설 운영계획의 근거로 활용할 수 있다.
- 금전적 인센티브 없이도 사전 약속, 귀가시간 역산, 조건별 저강도 일정, 호미곶을 여행의 두 번째 피니시라인으로 잇는 서사로 관광 동기를 만든다.

## 5. 기타 사항

- **비의료 원칙:** 서비스는 의료 진단이나 안전을 보장하지 않는다. 위험 증상은 관광 생성 중단과 의료지원 안내로 처리한다.
- **개인정보 최소화:** 상세 위치·자가 컨디션은 기능 수행에 필요한 범위에서만 사용하고, 서버에는 파생 상태와 익명 이벤트를 우선 저장한다.
- **3주 구현:** 1주차 PWA·페이스·E-UM Adapter, 2주차 Rule Engine·LLM·관광 일정, 3주차 재계획·오류 시나리오·3종 여정 데모를 완성한다.
- **검증 기준:** E-UM API HTTP 200과 기대 필드 확인, 키 누락·401·timeout·stale·빈 관광 결과·경로 실패 테스트, 웨어러블 없이 전체 여정 완료를 확인한다.
- **확장 방향:** PWA 검증 후 네이티브 iOS에서 HealthKit·WorkoutKit 기반 심박·거리·운동계획 연동을 검토한다.
